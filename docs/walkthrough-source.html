01 — The brief

What was asked for, and what that actually means

The assignment asks for a functional clone of Signal: registration, contacts, one-to-one and group conversations, and real-time messaging, inside an interface that looks and behaves like the real app.

02 — Decisions

Every choice, and the alternative it beat

These are the questions a reviewer is most likely to ask. Each answer names the option that was rejected, because a decision with no discarded alternative is not a decision.

Why FastAPI rather than Django?

The brief allows either. Django would need Channels plus a channel layer, which in practice means Redis, to hold a WebSocket. FastAPI speaks WebSocket natively in the same process, so real-time messaging needs no broker and the whole thing deploys as one service. Django's advantages here, the admin and the auth system, are not useful when authentication is a mocked OTP flow and the data is seeded by script.

Why SQLAlchemy 2.0 with Alembic rather than raw SQL?

Database design is a graded criterion, and Alembic turns the schema into reviewable history rather than one generated file. The 2.0 typed ORM also means relationships are declared once and the typing follows through into the service layer.

Why is a conversation one table instead of separate direct and group tables?

Because almost everything about a thread is identical whichever it is: it has members, messages, a last-activity timestamp, read cursors, mute and pin state. Splitting them would duplicate all of that and force every query to union two tables. A type column distinguishes them, and a sorted-pair dm_key with a unique index enforces the one rule that differs, which is that two people may only have one direct thread.

Why does read state live on the membership instead of the message?

Storing a read flag per message per member would mean writing one row per recipient every time someone opens a thread. Instead each membership holds a cursor, last_read_message_id, and the unread count is derived by counting messages after it. Opening a thread is then a single-row update regardless of how many messages were unread.

Then why does a separate receipts table exist?

Because the sender's check marks need per-recipient truth, and in a group one message is delivered many times. The cursor answers "what has this person read", which is what the badge needs. The receipts table answers "who has received and read this specific message", which is what the check marks need. They are different questions and conflating them produces wrong ticks in groups.

How do check marks work in a group, then?

They roll up. Delivered means every currently active member has a delivery row. Read means every active member has a read row. The status column on the message caches that rollup so the thread renders without an aggregate query per bubble.

What stops a duplicate message when the network is flaky?

The client generates a client_id before sending and the pair of sender and client id carries a unique index. A retry therefore hits the same row rather than creating a second one, and the optimistic bubble in the UI reconciles on the same key.

Why cursor pagination rather than offset?

An offset shifts underneath you. If a message arrives while someone is scrolling up through history, page two computed by offset either repeats or skips a row. A cursor anchored to a message id is stable regardless of what lands.

Where does the access token live, and why not localStorage?

In memory in the client module. A token in localStorage is readable by any script that gets injected into the page. The refresh token is an httpOnly cookie, which script cannot read at all, and it is stored server-side as a hash so logout can genuinely revoke it rather than just forgetting it.

What exactly is mocked about the encryption?

All of the cryptography. There is no X3DH key agreement and no Double Ratchet. What exists is the surface: each account carries a random identity key and registration id, each message carries a derived envelope hash, the thread header shows the encryption notice, and the contact sheet exposes a safety-number screen built from both parties' identity keys. Message bodies are stored as plaintext and the README says so rather than implying otherwise.

Why is presence real rather than random?

The brief allows mocking it, but the WebSocket hub already knows exactly who is connected. Writing is_online on connect and last_seen_at on disconnect is less code than faking it and it is actually correct.

03 — Architecture

How the pieces fit

Two deployables. The browser talks to FastAPI over HTTPS for everything that must survive a refresh, and holds one WebSocket open for everything that must arrive within a frame. The socket never grants authority it did not get from a REST call first.

The layering rule

Routers parse and validate, then call a service. Services hold the business rules and are the only layer that touches the ORM. The realtime hub is a transport, not a decision maker: it broadcasts what a service already committed. This is what keeps the modularity criterion satisfiable, and it is also why a router file never runs more than a few lines.

The life of a message

  1. The composer appends an optimistic bubble keyed by a client-generated client_id, at status sending.
  2. A POST persists the row and returns the server id. The optimistic bubble reconciles on client_id, so a retry cannot duplicate it. Status becomes sent.
  3. The hub fans a message.new event to every connected member except the sender, and a message.status event back to the sender.
  4. Each recipient's socket writes a receipt row on arrival. Once every active member has one, the sender's bubble becomes delivered.
  5. Opening the thread posts a read cursor, which fills read_at on the receipts. Once every active member has read, the bubble becomes read.
Why the order matters. Persistence happens before broadcast, never alongside it. If the write fails, nothing was announced. If the broadcast fails, the message is still in the database and the recipient picks it up on reconnect through replay-by-cursor. There is no state that exists only in a socket.

Reconnection

The client heartbeats every twenty-five seconds and reconnects with exponential backoff. On resume it sends the id of the last message it saw per open thread, and the server replays anything newer. That is why a dropped connection is invisible to the user rather than a reason to refresh.

07 — Built so far

Four phases complete, and how each was verified

Phases 0 through 3 and phase 5 are done: the scaffold, the data layer, authentication, the conversation and message API, and the Signal interface. Every phase in this project carries a gate, and a gate is something observed rather than asserted.

Phase 0 — Scaffold

  • A FastAPI application factory that mounts CORS, the media directory, the versioned router and a health probe, and nothing else. Routing, rules and transport each live elsewhere.
  • One settings object with development-safe defaults for every value, so a fresh clone runs with no .env file. Nothing in the codebase reads the environment directly.
  • Next.js with TypeScript and Tailwind v4, with the package structure already carved for later phases.

Gate passed: both dev servers start and the browser reaches the health route through the typed API client.

Phase 1 — Data layer

  • Eleven SQLAlchemy models across five modules, with the relationships and constraints the design depends on.
  • Alembic configured with render_as_batch, because SQLite cannot alter a column in place. The initial migration also creates the FTS5 index and its three sync triggers.
  • A deterministic seed producing eight accounts, a contact graph, five direct threads and three groups, with 166 scripted messages backdated across ten days, 299 receipts, mixed read state, reactions, a pinned thread, a disappearing timer, and one group where the demo account is a plain member.

Gate passed: a SQL client shows correct unread counts, pin order, roles, status rollup, and full-text search hits, with PRAGMA foreign_key_check clean.

Phase 2 — Authentication

  • The mocked verification flow modelled as the real one: expiry, an attempt counter, single-use codes, and invalidation of any outstanding code when a new one is requested.
  • Short-lived access tokens as JWTs; opaque refresh tokens stored only as a SHA-256 hash and rotated on every use.

Gate passed: a wrong code is refused with the attempts remaining, a correct one issues a session, refresh rotates, and a refresh after logout is rejected because the row was revoked rather than forgotten.

Phase 3 — Conversations and messages

  • One list query covering pin order, unread counts derived from each membership cursor, resolved titles for direct threads, and per-person pin, mute and archive.
  • Cursor-paged threads, idempotent send, soft delete, edit inside a window, one reaction per person, and the status rollup that collapses receipts into the sender's check marks.
  • Admin rules enforced server-side, with every membership change recorded as a system message, and a guard that prevents a group losing its last admin.

Gate passed: backend/scripts/smoke_test.py exercises 44 behaviours against a running server and all pass, including the paths that should fail.

Phase 5 — The interface

  • The three-pane shell: a 68px icon rail, a 320px conversation list and the thread. Below 768px the rail and list give up their space to the open conversation, as Signal does on a phone.
  • Signal values held as CSS variables mapped into the Tailwind theme, with the dark theme defined twice so the settings toggle can override the operating system in both directions.
  • Details reproduced rather than approximated: 72px rows with the unread pill, the 18px bubble radius dropping to 4px on the tail of a run, timestamps and check marks inside the bubble on the last message of a run only, coloured sender names in groups, centred date dividers and system messages, reaction pills overlapping the bubble edge, and a composer whose microphone becomes a send arrow once there is text.
  • Sign-in with one-tap seeded accounts, profile setup, the group and contact panel with the simulated safety number, settings with a working theme control, Coming Soon panes for calls and stories, toasts, and two keyboard shortcuts.

Gate passed: frontend/scripts/screenshots.mjs drives the real app in Chrome and captures ten screens at desktop and phone widths, in both themes, with no browser errors beyond the expected 401 from the refresh probe on a cold boot.

One real bug, found by testing rather than by reading. SQLite does not round-trip timezones: an aware datetime goes in and a naive one comes back, so the first comparison against the current time raised. It was fixed once with a UtcDateTime type decorator that normalises on write and re-attaches UTC on read, rather than patching each call site. Naive-UTC is stored deliberately, because the index range scans and the conversation list ordering rely on the stored text sorting lexically.
One deviation from the plan. The generator produced Next.js 16 rather than 15, and 16 enables cacheComponents by default. The live thread is therefore built as client components. No feature is affected.

Known risks, stated rather than discovered later

SQLite on a free host is not durable

Render's free tier has an ephemeral filesystem, so the database resets on redeploy. Either attach a persistent disk on the paid tier, or accept the reset and re-seed on boot. Whichever is chosen gets written into the README rather than left for the reviewer to find.

Vercel cannot hold a WebSocket

Serverless functions time out, so the socket must terminate on the backend service. The frontend therefore talks to two origins, which makes CORS and secure-socket configuration load-bearing rather than incidental.

Pixel fidelity has no upper bound

The brief asks for an exact match, which is not achievable in the time budget. Layout, spacing, colour and interaction behaviour are matched; small iconography differences are accepted, since the icon set here is hand-drawn rather than Signal's own.

09 — Running it

From a clone to a running app

Backend

cd backend
python -m venv .venv
.venv\Scripts\activate          # Windows
# source .venv/bin/activate     # macOS and Linux
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000

The API is then on port 8000, with interactive documentation at /docs. No .env file is needed locally; copy .env.example only to override something.

Frontend

cd frontend
npm install
npm run dev

The app is then on port 3000.

Assumptions a reader should know

  • Phone verification is mocked with a fixed code, and in development that code is returned in the response body so a reviewer never has to guess it.
  • Encryption is simulated. There is no key agreement and no ratchet. Message bodies are plaintext at rest and the documentation says so.
  • Online and last-seen state is driven by real socket connect and disconnect, not a random generator.
  • Everything is written from scratch for this assignment. No existing clone repository was used as a source, and no code was taken from the official Signal clients, which are GPL-licensed.
